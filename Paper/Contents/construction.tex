\section{Our Construction}
\label{sec:construction}

We begin by defining the relation chain that reduces the original matrix multiplication statement to a succinct SNARK-friendly relation (Section~\ref{sec:relation-chain}), then give the full protocol description (Section~\ref{sec:protocol-desc}), and conclude with a complexity analysis (Section~\ref{sec:complexity}).

\subsection{Relation Reduction Chain}
\label{sec:relation-chain}

Our construction proceeds through two successive reductions.
Each reduction preserves completeness exactly and introduces a bounded soundness error that we analyze in Section~\ref{sec:security}.

\paragraph{Input-commit phase}
The protocol starts by committing to the input and output matrices.
The prover row-wise encodes $\mat{A},\mat{B},\mat{C}$ and publishes Merkle roots
$\cm_A,\cm_B,\cm_C$ before the Freivalds challenge is sampled.
The input-root binding condition is that each root binds to
$\enc(\mat{A}),\enc(\mat{B}),\enc(\mat{C})$ for fixed matrices
$\mat{A},\mat{B},\mat{C} \in \mathbb{F}^{k \times k}$.
This is the same committed-oracle viewpoint used in code-based proof systems
such as Brakedown~\cite{golovnev2023brakedown} and
Orion~\cite{xie2022orion}: once a root is fixed, any accepted opening must be
the corresponding coordinate or column of the committed row-wise codeword.
The multiplication checker then proves the relation among these input roots
without arithmetizing the full matrix product.
Our artifact reports the online checking cost after the roots are available;
the raw cost of encoding matrices and building their roots is reported
separately when measured and is not included in the online proof-byte claims.
Throughout this section, $\merkle(\enc(\mat{M}))$ is shorthand for the Merkle
root over compact leaf handles
$(L_{M,1},\ldots,L_{M,n})$, where each handle is binding to the corresponding
encoded column $\enc(\mat{M})^{(j)}$.
For an encoded vector, $\merkle(\enc(v))$ analogously commits to handles for
the length-$n$ sequence of encoded coordinates.
The sampled values themselves are opened only to the Groth16 relation as
witness data; the auxiliary verifier sees handles and authentication paths.

\begin{definition}[Sampled-opening backend]\label{def:codecom-backend}
The online checker uses a black-box backend for sampled openings.
For each sampled object $\chi$ and query $j$, the Groth16 relation uses a
private value $a_{\chi,j}$ and the CC-SNARK backend publishes a
SNARK-side commitment $\Gamma_{\chi,j}$ to that value.
The auxiliary verifier sees the committed root $\cm_\chi$, a leaf handle
$L_{\chi,j}$, an opening path $\pi_{\chi,j}$, and an aggregate auxiliary proof
$\sigma_I$.
We write $\mathsf{AuxV}$ for the combined auxiliary verifier and
$\mathsf{LinkV}$ for its sampled-linking check after path verification.
The backend must provide three guarantees:

\emph{SNARK-side binding.}
If the Groth16 verifier accepts, every sampled value used in the fold equations
is bound by the CC-SNARK backend to its public commitment
$\Gamma_{\chi,j}$.
This property is part of the selected SNARK backend and is charged to
$\epsilon_{\mathsf{SNARK}}$.

\emph{Position opening.}
If the auxiliary verifier accepts, each $L_{\chi,j}$ is authenticated as the
leaf at position $j$ under the pre-query root $\cm_\chi$.

\emph{Sampled linking.}
If both verifiers accept, the value bound by $\Gamma_{\chi,j}$ is the same value
authenticated by $L_{\chi,j}$, except with probability
$\epsilon_{\mathsf{link}}(\lambda)$ over the backend security experiment.
The pre-query vector commitments have independent binding
error $\epsilon_{\mathsf{vec}}$, so the theorem charges
$\epsilon_{\mathsf{cc}}\le\epsilon_{\mathsf{vec}}+\epsilon_{\mathsf{link}}$.
\end{definition}

We do not require a new global code-commitment primitive.
Instead, $\protocol$ is stated relative to the committed-codeword viewpoint of
Brakedown~\cite{golovnev2023brakedown} and Orion~\cite{xie2022orion}, plus the
sampled-opening interface above.
The concrete artifact instantiates the interface with pre-query vector
commitments,
Merkle openings, and a batched auxiliary linking proof; Appendix~\ref{app:cplink-backend}
gives the algebraic relation, batching argument, and online-byte accounting.
The main construction and theorem use only the contract in
Table~\ref{tab:backend-contract}.

\paragraph{Artifact backend in one paragraph}
For the implementation evaluated in Section~\ref{sec:implementation}, each
sampled SNARK-side commitment and each authenticated leaf handle is a
Pedersen-style algebraic commitment to the same object.
The auxiliary proof is one batched quasi-adaptive NIZK (QA-NIZK) proof for a
linear relation~\cite{jutla2013shorter} linking all $Q=|\mathcal{S}|t$ sampled
SNARK-side/leaf commitment pairs.
Assuming CC-SNARK witness binding, binding of the handle
parameters, soundness of the QA-NIZK for the linear batch relation, and a
domain-separated batch challenge sampled after the batch statement is fixed, the
linking error is
$\epsilon_{\mathsf{link}}\le
\epsilon_{\mathsf{ped}}+\epsilon_{\mathsf{QA}}+Q/|\mathbb{F}|$.
The CRS, handle generators, and proving/verifying keys are setup material; the
reported byte counts in this paper are online proof bytes and exclude those
serialized setup objects.

\paragraph{QA-NIZK, CRS, and generator model}
The QA-NIZK is used only for the linear batch relation above, not for the matrix
multiplication relation itself.
Its CRS fixes the linear-relation verification parameters and the handle
generator description used by the sampled-linking backend.
Those generators may be serialized directly or expanded deterministically from a
public seed, depending on the concrete deployment; either way, the corresponding
bytes are setup/key/CRS material, not online proof bytes.
The current artifact reports online proof material and setup time, but not the
serialized size of these setup objects.

\paragraph{Backend boundary}
The security theorem is compositional: it proves the multiplication-checking
protocol relative to any backend satisfying Definition~\ref{def:codecom-backend}.
The input-commit phase may be run inside the same application protocol or by an
upstream data pipeline, but the roots must be fixed before $r$ is derived.
For a $k\times k$ matrix with codeword length $n$, producing an input root costs
$\Omega(kn)$ field work to encode rows and $\Omega(n)$ handle/hash work to form
the Merkle tree.
Static model-weight roots can amortize this cost over many inference requests;
per-request activation and output roots cannot.
The measurements in Section~\ref{sec:implementation} therefore report the
online multiplication-checking layer separately from raw-matrix encoding and
root construction.

\paragraph{The original relation $\mathcal{R}_{\mathsf{orig}}$}
The starting point is the statement that the prover knows matrices whose
\emph{encoded} commitments satisfy the multiplication relation.
The public instance is $(\cm_A, \cm_B, \cm_C)$ and the witness is
$(\mat{A}, \mat{B}, \mat{C})$; the relation $\mathcal{R}_{\mathsf{orig}}$
requires:
\[
\begin{gathered}
  \cm_A = \merkle(\enc(\mat{A})),\quad
  \cm_B = \merkle(\enc(\mat{B})),\\
  \cm_C = \merkle(\enc(\mat{C})),\quad
  \mat{A}\mat{B} = \mat{C}.
\end{gathered}
\]
Thus a matrix commitment binds the verifier to the row-wise codeword matrix
rather than to the raw matrix alone.
Since $\mathcal{C}$ is systematic, the raw matrix is also determined by the
first $k$ coordinates of each committed row.
Proving membership in $\mathcal{R}_{\mathsf{orig}}$ directly inside a SNARK would require $\mathcal{O}(k^3)$ multiplication constraints, which is exactly what we aim to avoid.

\paragraph{Reduction 1: Freivalds' randomization ($\mathcal{R}_{\mathsf{orig}} \rightsquigarrow \mathcal{R}_{\mathsf{Freivalds}}$)}
Using the verifier's random challenge $r \in \mathbb{F}$, define
$\vect{r} = (1, r, r^2, \ldots, r^{k-1})$ and introduce three intermediate
vectors
\[
  \vect{x}=\vect{r}\mat{A},\qquad
  \vect{y}=\vect{x}\mat{B},\qquad
  \vect{z}=\vect{r}\mat{C}.
\]
The Freivalds relation checks
\[
  \vect{r}\mat{A} = \vect{x},\qquad
  \vect{x}\mat{B} = \vect{y},\qquad
  \vect{r}\mat{C} = \vect{z},\qquad
  \vect{y}=\vect{z}.
\]
By the Schwartz--Zippel lemma, if $\mat{A}\mat{B} \neq \mat{C}$, then the
final equality fails except with probability at most $(k-1)/|\mathbb{F}|$ over
the choice of $r$.
This removes the cubic matrix-product check, but checking the three
vector-matrix products directly would still require quadratic circuit work.
No commitment to $\vect{x},\vect{y},\vect{z}$ is needed at this algebraic step;
those commitments are introduced next only to make the sampled proximity checks
non-adaptive.

\paragraph{Reduction 2: Proximity lifting ($\mathcal{R}_{\mathsf{Freivalds}} \rightsquigarrow \mathcal{R}_{\mathsf{Prox}}$)}
We now encode the matrices and intermediate vectors using a systematic
$\mathbb{F}$-linear code $\mathcal{C}: \mathbb{F}^k \to \mathbb{F}^n$ with
relative distance $\delta$, and replace the global vector-matrix checks with
\emph{local} consistency checks at random positions.
Let $I=(j_1,\ldots,j_t) \sample [n]^t$ be the ordered tuple of queried column
indices sampled independently with replacement, and let
$\mathcal{M} = \{\mat{A}, \mat{B}, \mat{C}\}$ denote the matrix set and
$\mathcal{W} = \{\vect{x}, \vect{y}, \vect{z}\}$ the intermediate-vector set.
Let $\mathcal{S}=\mathcal{M}\cup\mathcal{W}$ be the set of objects opened at
the sampled positions.
The matrix roots $\cm_A,\cm_B,\cm_C$ are fixed before $r$ is sampled.
After seeing $r$ but before seeing $I$, the prover commits to
$\vect{x},\vect{y},\vect{z}$ by sending pre-query vector commitments
$\mu_x,\mu_y,\mu_z$ and encoded-vector roots $\cm_x,\cm_y,\cm_z$.
The roots $\cm_x,\cm_y,\cm_z$ fix the encoded leaves that will later be opened,
but by themselves they do not force the Groth16 witness vectors
$\vect{x},\vect{y},\vect{z}$ to be chosen before $I$.
The commitments $\mu_x,\mu_y,\mu_z$ close this gap: the SNARK checks that its
vector witnesses open these pre-query commitments and then computes the
sampled code evaluations from the same vectors.
Without this vector binding, a malicious prover could wait for $I$ and choose
vectors that interpolate only the sampled coordinates.

The \emph{public instance} is
\[
  \stmt =
  \bigl(\{\cm_{\chi}\}_{\chi \in \mathcal{S}},\;
  \mu_x,\mu_y,\mu_z,\; r,\; I,\;
  \{\Gamma_{\chi,j}\}_{\chi\in\mathcal{S},\,j\in I}\bigr)
\]
and the private arithmetic-relation witness is
\[
  \begin{aligned}
  \wit = (&\vect{x},\, \vect{y},\, \vect{z},\,
    \{\omega_v\}_{v\in\mathcal{W}},\\
  &\bigl\{a_{\chi,j}\bigr\}_{j \in I,\, \chi \in \mathcal{S}}).
  \end{aligned}
\]
The auxiliary opening/linking proof data is
\[
  \mathsf{aux}_I =
  \left(\bigl\{L_{\chi,j},\pi_{\chi,j}\bigr\}
  _{j\in I,\,\chi\in\mathcal{S}},\sigma_I\right).
\]
For a matrix commitment, $a_{\chi,j}\in\mathbb{F}^{k}$ is the sampled encoded
column $\enc(\chi)^{(j)}$ used by the fold equation.
For a vector commitment, $a_{\chi,j}\in\mathbb{F}$ is the sampled encoded
coordinate.
The opening randomness $\rho_{\chi,j}$ belongs to the SNARK-side witness
commitment and to the auxiliary linking witness; it is not an R1CS witness
variable checked by an in-circuit opening constraint.
The resulting proximity-checking relation, denoted
$\mathcal{R}_{\mathsf{Prox}}$, requires
$(\stmt,\wit,\mathsf{aux}_I)$ to satisfy all of the following clauses.
In our implementation, clauses~\eqref{eq:vec-bind}--\eqref{eq:eq-check} are checked by Groth16;
clauses~\eqref{eq:path-check} and~\eqref{eq:link-check} are checked by
$\mathsf{AuxV}$ over the same transcript and SNARK-side commitments.
\begingroup
\scriptsize
\begin{align}
  &\forall v\in\mathcal{W}{:}\quad
    \vecBindV(\mu_v,v,\omega_v)=1,
    \tag{VEC}\label{eq:vec-bind}\\
  &\forall v\in\mathcal{W},\,j\in I{:}\quad
    a_{v,j}=\enc(v)_j,
    \tag{RS}\label{eq:rs-check}\\
  &\forall j \in I{:}\quad
    a_{x,j} = \fold\!\bigl(a_{A,j},\,\vect{r}\bigr), \tag{FOLD-A}\label{eq:fold-A}\\
  &\forall j \in I{:}\quad
    a_{y,j} = \fold\!\bigl(a_{B,j},\,\vect{x}\bigr), \tag{FOLD-B}\label{eq:fold-B}\\
  &\forall j \in I{:}\quad
    a_{z,j} = \fold\!\bigl(a_{C,j},\,\vect{r}\bigr), \tag{FOLD-C}\label{eq:fold-C}\\
  &\forall j \in I{:}\quad
    a_{y,j} = a_{z,j}, \tag{EQ}\label{eq:eq-check}\\
  &\forall \chi \in \mathcal{S},\, j \in I{:}\quad
    \openV(\pi_{\chi,j},L_{\chi,j},\cm_{\chi},j)=1
    \tag{PATH}\label{eq:path-check}
    \\
  &\mathsf{LinkV}(\stmt,I,
    \big((\Gamma_{\chi,j_q},L_{\chi,j_q})\big)
      _{\chi\in\mathcal{S},\,1\le q\le t},\sigma_I)=1
    \tag{LINK}\label{eq:link-check}
\end{align}
\endgroup
Here $\forall j \in I$ ranges over every sampled position in the ordered tuple,
including repetitions.
The CC-SNARK backend is the bridge between the private Groth16
witness and the auxiliary opening world: the fold equations use $a_{\chi,j}$,
and SNARK verification binds that same witness slot to the public commitment
$\Gamma_{\chi,j}$.
Equation~\eqref{eq:path-check} uses the selected position-opening verifier on
the compact leaf handle $L_{\chi,j}$.
For the transparent Merkle instantiation, this is $\merkleV$ with the queried
index included in the leaf domain.
Equation~\eqref{eq:link-check} is the backend check that links the SNARK-side
commitment $\Gamma_{\chi,j}$ to the authenticated leaf handle $L_{\chi,j}$.
Equation~\eqref{eq:vec-bind} is what ties the vectors used by the circuit to
the pre-query vector commitments that were fixed before $I$ was sampled.
Sending $\mu_x,\mu_y,\mu_z$ alone would not force the circuit witness to use the
committed vectors.
Equation~\eqref{eq:rs-check} computes the sampled RS/code evaluation for each
intermediate vector inside the circuit.
In the $\fmQA$ artifact, vector-binding openings, sampled RS evaluations, and fold
equations are included in the Groth16 relation, while Merkle path verification
and sampled linking are auxiliary checks bound to the same transcript and to the
SNARK-side commitments.
The security proof uses only vector-commitment binding, sampled witness-to-leaf
link consistency, and position binding of the opening layer.

The critical property is that the Groth16 relation involves only
$\mathcal{O}(|I| \cdot k)$ constraints for the fold operations, sampled RS
evaluations, and vector-binding checks.
Merkle authentication and sampled-linking verification are auxiliary online
checks whose cost is reported separately.
Since $|I|$ is a security-parameter-sized constant independent of $k$, the
in-circuit checking relation is \emph{linear in $k$}.

\paragraph{Intermediate-binding cost}
The vector-binding checks in~\eqref{eq:vec-bind} force the prover to commit to fixed
vectors $\vect{x},\vect{y},\vect{z}$ before the query tuple is sampled.
The CC-SNARK witness binding of $\Gamma_{\chi,j}$ and the link check in
\eqref{eq:link-check} then force each sampled external opening to equal the
value used by the in-circuit fold relation; for intermediate vectors,
\eqref{eq:rs-check} also forces this value to be the corresponding code
evaluation $\enc(v)_j$.
Without the pre-query vector commitments, a cheating prover could choose
sampled openings first and then interpolate a vector that matches only those
positions, defeating the distance-based soundness argument.
Analogously, the input matrix roots $\cm_A,\cm_B,\cm_C$ must be fixed
commitments to row-wise encodings of $\mat{A},\mat{B},\mat{C}$ before the
Freivalds challenge.
For Reed--Solomon-style encodings, a sampled coordinate $\enc(v)_j$ can be
computed by evaluating the degree-$(k-1)$ interpolation polynomial at the queried
domain point, costing $\mathcal{O}(k)$ constraints per sampled coordinate.
Thus the sampled intermediate checks contribute $\mathcal{O}(tk)$ constraints.
A fallback backend that proves full dense codeword validity inside the circuit
would instead require $\mathcal{O}(k(n-k))$ work for a dense generator matrix.
We discuss the trade-off in Section~\ref{sec:complexity}.

\subsection{Protocol Description}
\label{sec:protocol-desc}

We now give the full specification of $\protocol$.
Let $\mathcal{C}: \mathbb{F}^k \to \mathbb{F}^n$ be a systematic linear code with relative distance $\delta$ and $\merkle$ denote the Merkle tree commitment.
Let $\mathcal{M} = \{\mat{A}, \mat{B}, \mat{C}\}$ be the matrix set,
$\mathcal{W} = \{\vect{x}, \vect{y}, \vect{z}\}$ the intermediate-vector set,
and $\mathcal{S} = \mathcal{M} \cup \mathcal{W}$ the objects opened at sampled
positions.
The prover first commits to $\enc(\mat{A}),\enc(\mat{B}),\enc(\mat{C})$ and
sends the input roots $(\cm_A,\cm_B,\cm_C)$ before the challenge is derived.
The protocol $\protocol$ operates between a prover $\mathcal{P}$ and verifier $\mathcal{V}$ as shown in Figure~\ref{fig:protocol}.

\paragraph{Remark on the SNARK relation}
The SNARK proof $\pi$ attests to the in-circuit part of
$\mathcal{R}_{\mathsf{Prox}}$ defined in Section~\ref{sec:relation-chain};
full transcript acceptance additionally requires the auxiliary opening and
linking verifiers to accept.
The implemented verifier checks three groups of conditions, split between the
Groth16 circuit and auxiliary verifiers.
First, constraint~\eqref{eq:vec-bind} ties the pre-query vector commitments
$\mu_x,\mu_y,\mu_z$ to the same $\vect{x},\vect{y},\vect{z}$ used in the fold
checks.
The CC-SNARK backend binds each sampled value used by the
circuit to the public commitment $\Gamma_{\chi,j}$ through the Groth16
verification equation; this is not a separate arithmetic constraint.
Constraints~\eqref{eq:rs-check}--\eqref{eq:eq-check} verify the sampled RS,
fold, and equality checks at each $j \in I$ inside the Groth16 circuit.
Second, the auxiliary backend checks~\eqref{eq:link-check}, linking each public
SNARK-side commitment $\Gamma_{\chi,j}$ to the authenticated external leaf handle
$L_{\chi,j}$.
Third, the auxiliary opening verifier checks~\eqref{eq:path-check} for all
Merkle opening proofs over the leaf handles.
The public statement $\stmt$ consists of the commitment roots
$\{\cm_\chi\}_{\chi \in \mathcal{S}}$, the intermediate vector commitments
$\mu_x,\mu_y,\mu_z$, the challenge $r$, the query tuple $I$, and the sampled
SNARK-side commitments $\{\Gamma_{\chi,j}\}$.
The relation witness $\wit$ consists of the intermediate vectors, openings of
their vector commitments, and the sampled matrix columns or vector leaves used
by the fold equations.
The randomness $\{\rho_{\chi,j}\}$ is consumed by the CC-SNARK/linking
backend, not by an in-circuit opening check.

\paragraph{Non-interactive variant}
The protocol as described is a three-round public-coin interactive protocol.
By applying the Fiat--Shamir heuristic~\cite{fiat1987prove} in the random oracle model, it can be made non-interactive using domain-separated transcript hashes:
\[
\begin{gathered}
  \mathsf{Cm}_{ABC}\gets\Hash(\para,\cm_A,\cm_B,\cm_C),\\
  r \gets \Hash(\textsf{FMM-r},\mathsf{Cm}_{ABC}).
\end{gathered}
\]
and
\[
\begin{gathered}
  \mathsf{Cm}_{XYZ}\gets
    \Hash(\para,r,\mu_x,\mu_y,\mu_z,\cm_x,\cm_y,\cm_z),\\
  T_{\mathsf{qry}} \gets (\mathsf{Cm}_{ABC},\mathsf{Cm}_{XYZ}),\\
  I \gets \textsf{Sample}_{t}\!\left(\Hash(\textsf{FMM-I},T_{\mathsf{qry}})\right).
\end{gathered}
\]
The resulting non-interactive proof consists of the commitment roots, the
intermediate vector commitments, the transcript-derived challenges, the
sampled SNARK-side commitments $\{\Gamma_{\chi,j}\}$, and the SNARK proof $\pi$.
Merkle leaf handles, authentication paths, and sampled-linking material are
auxiliary proof data verified by the corresponding backend.
Raw sampled matrix columns are not serialized as proof data; they remain
private Groth16 witness values bound to the public SNARK-side commitments.

\paragraph{Security of the non-interactive variant}
A potential concern with the Fiat--Shamir transform for proximity-based protocols is a \emph{grinding attack}: a malicious prover could try many transcript prefixes until the derived challenge $r$ or query tuple $I$ is favorable.
The random-oracle theorem accounts for this by the standard
$\epsilon_{\mathsf{FS}}(q_H)$ loss in Theorem~\ref{thm:security}.
For intuition, consider grinding only the intermediate commitments after $r$ is fixed.
Suppose the adversary has committed to $(\cm_A, \cm_B, \cm_C)$ (and hence to fixed encoded matrices) and, after receiving $r$, is searching for intermediate vector commitments and encoded-vector roots such that the transcript-derived query tuple $I$ avoids the disagreement set $D$ of some fold or equality check.
If any of the four checks fails globally, then $|D| \ge \delta n$ by the minimum-distance property.
For a single random query $j \in [n]$, the probability of $j \notin D$ is at most $1 - \delta$; for $t$ independent queries it is $(1-\delta)^t$.
Choosing $t$ as in Section~\ref{sec:security} makes the union-bounded proximity term $4(1-\delta)^t$ at most $2^{-\lambda}$.
Each trial of the grinding attack produces an independently random $I$ in the random oracle model because the query hash binds the full transcript, so the probability that $q$ grinding attempts yield a favorable $I$ is at most $q \cdot 4(1-\delta)^t$.
For any $\ppt$ adversary, $q$ is polynomially bounded in $\lambda$, giving a total success probability of $\mathsf{negl}(\lambda)$.
Hence the non-interactive protocol retains the soundness bound of
Theorem~\ref{thm:security} in the random oracle model, plus the stated
Fiat--Shamir loss.

\paragraph{Zero-knowledge extension}
The protocol as stated is a \emph{verifiable computation} protocol and does not conceal the inputs $\mat{A}, \mat{B}, \mat{C}$ from the verifier.
We do not claim zero knowledge for $\protocol$.
A zero-knowledge variant would require replacing the Merkle tree commitments
with hiding commitments, using a zero-knowledge SNARK backend for $\pi$, and
masking the intermediate vectors and sampled openings so that the transcript
does not reveal linear information about the committed matrices.
The auxiliary opening/linking material would also need a separate simulation
argument.
We therefore treat zero knowledge as future work rather than as a property of
the construction analyzed in this paper.


\subsection{Complexity Analysis}
\label{sec:complexity}

We analyze the costs of $\protocol$.

\paragraph{Prover computation}
We separate the cost of producing the claimed output matrix and input roots from
the cost of proving that the roots satisfy the multiplication claim.
Computing $\mat{C}=\mat{A}\mat{B}$ is application work shared by all approaches
and is not part of the checking-layer comparison.
Likewise, producing input roots for raw matrices is an input-commitment cost:
with linear-time codes it takes $\mathcal{O}(kn)$ field work for a
$k\times k$ matrix, plus handle and hash work to form the root.
After those roots are fixed, the prover's dominant online checking-layer costs
are:
\begin{enumerate}[label=(\roman*)]
  \item \emph{Vector computation}: Computing $\vect{x}, \vect{y}, \vect{z}$ costs $\mathcal{O}(k^2)$ in total.
  \item \emph{Intermediate-vector roots}: Encoding $\vect{x},\vect{y},\vect{z}$ and forming their roots costs $\mathcal{O}(n)$ for constant-rate linear codes.
  \item \emph{SNARK proving}: The circuit size is $\mathcal{O}(t \cdot k + E_{\mathsf{vec}}(k))$ for the fold checks, sampled RS evaluations, and vector-binding constraints. Merkle authentication, CC-SNARK witness commitments, and sampled-linking work are backend costs included in the reported proving, verification, and online-byte breakdowns.
\end{enumerate}

\paragraph{Verifier computation}
The verifier performs SNARK verification together with any commitment/linking
checks required by the chosen backend.
For a pairing-based SNARK whose public input consists only of the roots,
challenge, and query indices, the core SNARK verification is $\mathcal{O}(1)$.
For transparent or linking-heavy backends, verification may scale with the
public input or linking proof bytes; the concrete behavior is reported in
Section~\ref{sec:implementation}.

\paragraph{Communication}
The communication depends on the commitment layer.
With the sampled-opening backend evaluated in this paper, the proof
contains the SNARK proof, vector commitments, public SNARK-side commitments,
authentication paths, and auxiliary linking material for the queried objects.
The raw sampled matrix columns contain $\mathcal{O}(tk)$ field elements, but
they are Groth16 witness values rather than serialized proof bytes.
The serialized auxiliary material is compact: SNARK-side commitments, leaf
handles, Merkle paths, and link proofs scale as
$\mathcal{O}(t\log n+E_{\mathsf{link}}(k))$ for fixed security parameter.
This accounting explains the sub-megabyte online proof sizes reported in
Section~\ref{sec:implementation} and Appendix~\ref{app:eval-details}; making
the sampled columns public would instead add $\Theta(tk)$ field elements.

\paragraph{Circuit size comparison}
Table~\ref{tab:cost-summary} summarizes the asymptotic costs.
Na\"ive arithmetization uses $\mathcal{O}(k^3)$ constraints.
Freivalds' algorithm alone uses $\mathcal{O}(k^2)$.
The online checker achieves
\[
  \mathcal{O}\bigl(tk + E_{\mathsf{vec}}(k)\bigr)
  \text{ in-circuit work}
\]
plus $\mathcal{O}(t\log n+E_{\mathsf{link}}(k))$ auxiliary opening/linking
work.
The in-circuit term covers the fold checks, sampled RS evaluations, and
vector-binding checks.
The auxiliary term covers Merkle authentication and sampled-linking
verification over compact sampled commitments and leaf handles.
The older notation $E_{\mathsf{cc}}(k)$ denotes the combined
vector-binding/linking cost, with
$E_{\mathsf{cc}}(k)=E_{\mathsf{vec}}(k)+E_{\mathsf{link}}(k)$ for the current
artifact.
For dense general codes, a full in-circuit codeword-validity fallback gives
$E_{\mathsf{cc}}(k)=\mathcal{O}(k(n-k))$, which is $\mathcal{O}(k^2)$ at
constant rate.
For the sampled-opening backend evaluated in this paper, the online sampled
encoding work is already included in the $\mathcal{O}(tk)$ term.
Setting
\[
  t = \left\lceil
    \frac{\lambda+2}{\log_2(1/(1-\delta))}
  \right\rceil
\]
then gives $\mathcal{O}(k)$ in-circuit work and $\mathcal{O}(\log k)$
serialized auxiliary opening material for fixed security parameter, with
concrete sizes discussed in Section~\ref{sec:implementation}.
