\subsection{Relation Reduction Chain}
\label{sec:relation-chain}

Our construction proceeds through two successive reductions.
Each reduction preserves completeness exactly and introduces a bounded soundness error that we analyze in Section~\ref{sec:security}.

\paragraph{Input-commitment model}
Following the committed-oracle viewpoint common in code-based proof systems
such as Brakedown~\cite{golovnev2023brakedown} and Orion~\cite{xie2022orion},
we take the input matrix commitments as certified public inputs.
Concretely, $\cm_A,\cm_B,\cm_C$ are assumed to bind to row-wise encodings
$\enc(\mat{A}),\enc(\mat{B}),\enc(\mat{C})$ of some matrices
$\mat{A},\mat{B},\mat{C} \in \mathbb{F}^{k \times k}$.
Certification means that every accepting opening of $\cm_M$, for
$M \in \{\mat{A},\mat{B},\mat{C}\}$, is a coordinate or column of
$\enc(M)$ for a fixed matrix $M$ determined before the verifier samples the
Freivalds challenge.
This certification may be supplied by the surrounding committed-codeword
system, by a public generation process, or by a separate input-opening proof.
It is a precondition of the multiplication-checking protocol rather than an
online cost charged to $\protocol$.
The goal of $\protocol$ is to verify the multiplication relation among these
committed matrices without arithmetizing the full matrix product.
The concrete deployment interface used for our claims is therefore:
an offline certification layer publishes $(\cm_A,\cm_B,\cm_C)$ together with
the assertion that they are binding commitments to row-wise encoded matrices;
the online checker receives only these certified roots and proves the
multiplication relation over them.
If the deployment starts from raw matrices or ML tensors, the cost of producing
and certifying those roots must be added separately.
Throughout this section, $\merkle(\enc(\mat{M}))$ is shorthand for the Merkle
root over compact leaf handles
$(L_{M,1},\ldots,L_{M,n})$, where each handle is binding to the corresponding
encoded column $\enc(\mat{M})^{(j)}$.
For an encoded vector, $\merkle(\enc(v))$ analogously commits to handles for
the length-$n$ sequence of encoded coordinates.
The sampled values themselves are opened only to the Groth16 relation as
witness data; the auxiliary verifier sees handles and authentication paths.

\begin{definition}[CP-linked sampled-opening backend]\label{def:codecom-backend}
For each sampled object $\chi\in\mathcal{S}$ and query $j\in I$, let
$d_\chi=k$ for matrix columns and $d_\chi=1$ for vector coordinates, so the
sampled value is $a_{\chi,j}\in\mathbb{F}^{d_\chi}$.
A CP-linked sampled-opening backend consists of the following algorithms.

\emph{Setup.}
$\mathsf{Link.Setup}(1^\lambda,d_{\max})$ produces public parameters included
in $\para$, including the generators or keys used by the handle commitments.

\emph{Wire handle.}
$\Gamma_{\chi,j}\gets\wireCom(\para,a_{\chi,j};\rho_{\chi,j})$ commits to the
sampled value used by the Groth16 relation.
The predicate
$\wireV(\para,\Gamma_{\chi,j},a_{\chi,j},\rho_{\chi,j})=1$ is arithmetized
inside Groth16.

\emph{Leaf handle and opening.}
The external committed object stores compact leaf handles
$L_{\chi,j}$, one per encoded column or coordinate.
For Pedersen-style handles, this means
$L_{\chi,j}\gets\wireCom(\para,a_{\chi,j};\eta_{\chi,j})$ for leaf-opening
randomness $\eta_{\chi,j}$.
The auxiliary opening verifier checks
$\openV(\pi_{\chi,j},L_{\chi,j},\cm_\chi,j)=1$.
The value $a_{\chi,j}$ itself is not serialized to the verifier.

\emph{CP-link.}
Let $Q=|\mathcal{S}|t$ and enumerate the sampled pairs
$q=(\chi,j)\in\mathcal{S}\times I$.
Let
\[
  P_I=\{(\chi,j,\Gamma_{\chi,j},L_{\chi,j})\}_{\chi,j}.
\]
The batch transcript tag is
\[
T_I=\Hash(\textsf{FMM-link-batch},\mathsf{Cm}_{ABC},\mathsf{Cm}_{XYZ},I,P_I).
\]
For each sampled pair, the link witness is
$\Delta_{\chi,j}=\rho_{\chi,j}-\eta_{\chi,j}$.
The prover sends one batched auxiliary proof
\[
  \tau_I\gets
  \cpLinkP(\para,T_I,\{(\Gamma_{\chi,j},L_{\chi,j})\}_{\chi,j},
  \{\Delta_{\chi,j}\}_{\chi,j}).
\]
The public batch statement is
$(\para,T_I,\{(\Gamma_{\chi,j},L_{\chi,j})\}_{\chi,j})$; the witnesses are the
differences between the wire-handle and leaf-handle opening randomnesses.
The verifier accepts the batch iff
$\cpLinkV(\para,T_I,\{(\Gamma_{\chi,j},L_{\chi,j})\}_{\chi,j},\tau_I)=1$.
The logical per-object relation is still
$\Gamma_{\chi,j}-L_{\chi,j}=\Delta_{\chi,j}H$; batching only changes the
serialized proof object.
The same syntax handles matrix columns and vector coordinates by varying
$d_\chi$.

\emph{Completeness.}
For honestly generated handles and openings, $\wireV$, $\openV$, and
$\cpLinkV$ all accept.

\emph{Binding and linking soundness.}
The backend has error $\epsilon_{\mathsf{link}}(\lambda)$ if no $\ppt$
adversary can produce an accepting batch proof $\tau_I$, accepted Merkle
openings, and Groth16 witness openings such that some sampled pair has
$\wireV(\para,\Gamma,a,\rho_\Gamma)=1$ and
$\openV(\pi,L,\cm,j)=1$, while no $\eta$ makes the authenticated leaf handle
$L$ open to the same value $a$, except with probability
$\epsilon_{\mathsf{link}}(\lambda)$.
The intermediate-vector message commitments have independent binding error
$\epsilon_{\mathsf{msg}}$.
Thus the theorem uses
$\epsilon_{\mathsf{cc}}\le\epsilon_{\mathsf{msg}}+\epsilon_{\mathsf{link}}$.
\end{definition}

\paragraph{Concrete handle instantiation and cost}
The $\fmQA$ artifact uses a Pedersen-style~\cite{pedersen1991non} algebraic
handle interface:
\[
  \Gamma=\rho_\Gamma H+\sum_{\ell=1}^{d_\chi} a_\ell G_\ell ,
  \qquad
  L=\rho_L H+\sum_{\ell=1}^{d_\chi} a_\ell G_\ell ,
\]
with the scalar case obtained by setting $d_\chi=1$.
Leaf handles use the same commitment syntax and are the values authenticated by
the Merkle tree.
Groth16 checks the wire-handle opening equation for the sampled witness value;
the QA-NIZK CP-link proves that the public wire handle and authenticated leaf
handle open to the same committed object under the transcript tag $T_{\chi,j}$.
Concretely, the link witness is the scalar
$\Delta=\rho_\Gamma-\rho_L$, and the checked relation is
\[
  \Gamma-L=\Delta H .
\]
Thus the link proof itself is independent of the object dimension $d_\chi$:
matrix columns use $d_\chi=k$ and vector coordinates use $d_\chi=1$, but after
both handles are formed, equality of the committed object is reduced to the
one-dimensional difference-opening statement above.
The dimension affects handle generation and the in-circuit wire-opening check,
not the serialized CP-link proof length.
Under the binding of the handle commitment, collision resistance/position
binding of the Merkle opening, and soundness of the QA-NIZK link proof, a
prover cannot use one sampled value in the Groth16 fold equations and a
different value in the auxiliary opening layer.
The current CSV reports this backend at aggregate granularity: handle-opening,
message-opening, sampled RS, and fold constraints are included in the Groth16
constraint count; Merkle and CP-link work are reported as proof bytes and
auxiliary verification time.

\begin{theorem}[Batched CP-link backend]\label{thm:cp-link-backend}
Assume the Pedersen handle parameters are generated so that the vector handle
commitment is binding, the QA-NIZK link proof for the linear batch relation is
sound, and the batching challenge is sampled by the Fiat--Shamir random oracle
after $T_I$ and all $(\Gamma_{\chi,j},L_{\chi,j})$ pairs are fixed.
For $Q=|\mathcal{S}|t$ sampled objects, the batched CP-link verifier accepts a
false batch with probability at most
$\epsilon_{\mathsf{ped}}+\epsilon_{\mathsf{QA}}+Q/|\mathbb{F}|$.
Here $\epsilon_{\mathsf{ped}}$ is the binding error of the handle commitment
parameters and $\epsilon_{\mathsf{QA}}$ is the soundness error of the QA-NIZK
proof for the randomized linear relation.
The artifact serializes the $Q$ logical relations as one batched QA-NIZK proof
$\tau_I$, the $128$-byte CP-link component reported in
Section~\ref{sec:implementation}; generator/CRS bytes are setup material and
are not included in this online proof-size claim.
\end{theorem}
Appendix~\ref{app:cplink-backend} gives the proof sketch and batching
equation.

We do not require a new global code-commitment primitive.
Instead, $\protocol$ is stated relative to the committed-codeword viewpoint of
Brakedown~\cite{golovnev2023brakedown} and Orion~\cite{xie2022orion}, plus the
sampled witness-to-leaf linking interface above.
Operationally, the backend can be instantiated by a Brakedown/Orion-style
code-commitment layer, or by the CP-linked implementation used in our artifact:
message commitments to $\vect{x},\vect{y},\vect{z}$ are fixed before $I$ is
derived, the circuit uses sampled matrix columns and computes sampled RS
evaluations $\enc(v)_j$, Merkle membership authenticates compact leaf handles,
and CP-link proofs connect the Groth16 wire handles for those sampled objects
to the authenticated Merkle leaves.

\paragraph{Backend contract used by the theorem}
Theorem~\ref{thm:security} uses only the following backend facts:
(i)~the input matrix roots are certified commitments to fixed row-wise
codewords before $r$ is sampled;
(ii)~the intermediate message commitments and encoded-vector roots are sent
before $I$ is sampled;
(iii)~the Groth16 relation binds every sampled matrix column or vector leaf it
uses to a public wire handle $\Gamma_{\chi,j}$;
(iv)~accepted Merkle and CP-link checks bind each $\Gamma_{\chi,j}$ to the
corresponding leaf handle under the pre-query root $\cm_\chi$; and
(v)~accepted message-opening checks bind sampled intermediate-vector
coordinates to $\enc(v)$ for the pre-query vector $v$ as in
Definition~\ref{def:codecom-backend}.
No part of the proof relies on a new algebraic assumption specific to
$\protocol$ beyond this committed-codeword interface.

\paragraph{Backend boundary}
The security theorem is compositional: it proves the multiplication-checking
protocol relative to any backend satisfying Definition~\ref{def:codecom-backend}.
An end-to-end system must choose one concrete input-certification interface and
specify its contribution to preprocessing, public input size, and setup.
Our implementation instantiates the intermediate-vector backend with message
commitments, Merkle openings, and QA-NIZK/CP-link checks for sampled encoded
coordinates; it does not certify raw input matrices by itself.
For the GPT-2 case study, static model-weight roots can be certified once and
reused, while per-request activation/output roots must be certified by the
surrounding computation pipeline.
Thus the GPT-2 experiment is a checking-layer case study over certified roots,
not an end-to-end raw-tensor VC measurement.

\paragraph{Concrete deployment model for certified roots}
The intended deployment is a two-layer pipeline.
An offline or upstream certification layer encodes each raw matrix or tensor,
forms the compact leaf handles, and publishes the Merkle root together with the
claim that the root binds to the encoded object.
The online multiplication checker then proves only the multiplication relation
among these certified roots.
For a $k\times k$ matrix with codeword length $n$, this certification layer
performs $\Omega(kn)$ field work to produce the row-wise codeword and
$\Omega(n)$ handle/hash work to form the root; a vector root costs
$\Omega(n)$ plus the selected message-commitment cost.
Static model-weight roots can amortize this cost over many inference requests.
Per-request activation and output roots require an upstream tensor-commitment
step; the measurements in Section~\ref{sec:implementation} remain end-to-end
beneficial only when the amortized certification cost is below the online
checking-layer savings reported there.

\paragraph{The original relation $\mathcal{R}_{\mathsf{orig}}$}
The starting point is the statement that the prover knows matrices whose
\emph{encoded} commitments satisfy the multiplication relation.
The public instance is $(\cm_A, \cm_B, \cm_C)$ and the witness is
$(\mat{A}, \mat{B}, \mat{C})$; the relation $\mathcal{R}_{\mathsf{orig}}$
requires:
\[
\begin{gathered}
  \cm_A = \merkle(\enc(\mat{A})),\quad
  \cm_B = \merkle(\enc(\mat{B})),\\
  \cm_C = \merkle(\enc(\mat{C})),\quad
  \mat{A}\mat{B} = \mat{C}.
\end{gathered}
\]
Thus a matrix commitment binds the verifier to the row-wise codeword matrix
rather than to the raw matrix alone.
Since $\mathcal{C}$ is systematic, the raw matrix is also determined by the
first $k$ coordinates of each committed row.
Proving membership in $\mathcal{R}_{\mathsf{orig}}$ directly inside a SNARK would require $\mathcal{O}(k^3)$ multiplication constraints, which is exactly what we aim to avoid.

\paragraph{Reduction 1: Freivalds' randomization ($\mathcal{R}_{\mathsf{orig}} \rightsquigarrow \mathcal{R}_{\mathsf{Freivalds}}$)}
Using the verifier's random challenge $r \in \mathbb{F}$, we construct the vector $\vect{r} = (1, r, r^2, \ldots, r^{k-1})$ and define intermediate vectors $\vect{x} = \vect{r}\mat{A}$, $\vect{y} = \vect{x}\mat{B}$, $\vect{z} = \vect{r}\mat{C}$.
Let $\mathcal{S} = \{\mat{A}, \mat{B}, \mat{C}, \vect{x}, \vect{y}, \vect{z}\}$ denote the full set of committed objects.
The instance is $(\{\cm_{\chi}\}_{\chi \in \mathcal{S}}, r)$ and the witness is $\{\chi\}_{\chi \in \mathcal{S}}$;
the relation $\mathcal{R}_{\mathsf{Freivalds}}$ requires:
\begin{align*}
  &\textstyle\bigwedge_{\chi \in \mathcal{S}}\; \cm_{\chi} = \merkle(\enc(\chi)), \\
  &\vect{r}\mat{A} = \vect{x} \;\land\; \vect{x}\mat{B} = \vect{y}, \\
  &\vect{r}\mat{C} = \vect{z} \;\land\; \vect{y} = \vect{z}.
\end{align*}
By the Schwartz--Zippel lemma, if $\mat{A}\mat{B} \neq \mat{C}$, then $\vect{y} \neq \vect{z}$ with probability at least $1 - (k-1)/|\mathbb{F}|$.
Note that while this relation eliminates the $\mathcal{O}(k^3)$ matrix product, verifying the vector-matrix products still costs $\mathcal{O}(k^2)$ each.

\paragraph{Reduction 2: Proximity lifting ($\mathcal{R}_{\mathsf{Freivalds}} \rightsquigarrow \mathcal{R}_{\mathsf{SNARK}}$)}
We now encode all matrices and vectors using a systematic $\mathbb{F}$-linear code $\mathcal{C}: \mathbb{F}^k \to \mathbb{F}^n$ with relative distance $\delta$, and replace the global vector-matrix checks with \emph{local} consistency checks at random positions.
Let $I=(j_1,\ldots,j_t) \sample [n]^t$ be the ordered tuple of queried column
indices sampled independently with replacement, and let
$\mathcal{M} = \{\mat{A}, \mat{B}, \mat{C}\}$,
$\mathcal{W} = \{\vect{x}, \vect{y}, \vect{z}\}$ denote the matrix set and
vector set respectively.

The \emph{public instance} is
\[
  \stmt =
  \bigl(\{\cm_{\chi}\}_{\chi \in \mathcal{S}},\;
  \mu_x,\mu_y,\mu_z,\; r,\; I,\;
  \{\Gamma_{\chi,j}\}_{\chi\in\mathcal{S},\,j\in I}\bigr)
\]
and the \emph{Groth16 witness} is
\[
  \begin{aligned}
  \wit = (&\vect{x},\, \vect{y},\, \vect{z},\,
    \omega_x,\omega_y,\omega_z,\\
  &\bigl\{a_{\chi,j},\rho_{\chi,j}\bigr\}_{j \in I,\, \chi \in \mathcal{S}}).
  \end{aligned}
\]
The auxiliary opening/linking proof data is
\[
  \mathsf{aux}_I =
  \left(\bigl\{L_{\chi,j},\pi_{\chi,j}\bigr\}
  _{j\in I,\,\chi\in\mathcal{S}},\tau_I\right).
\]
The prover additionally uses the leaf-handle randomness $\eta_{\chi,j}$ and
the difference witness $\Delta_{\chi,j}$ to create the batched CP-link proof
$\tau_I$, but these values are not serialized except through that proof.
For a matrix commitment, $a_{\chi,j}\in\mathbb{F}^{k}$ is the sampled encoded
column $\enc(\chi)^{(j)}$ used by the fold equation.
For a vector commitment, $a_{\chi,j}\in\mathbb{F}$ is the sampled encoded
coordinate.
The full online acceptance relation requires
$(\stmt,\wit,\mathsf{aux}_I)$ to satisfy all of the following clauses.
Clauses~\eqref{eq:msg-check}--\eqref{eq:eq-check} are checked by Groth16;
clauses~\eqref{eq:path-check} and~\eqref{eq:link-check} are checked by
$\mathsf{AuxV}$ over the same transcript and public handles.
\begingroup
\scriptsize
\begin{align}
  &\msgV(\mu_x,\vect{x},\omega_x)=1
    \;\land\; \msgV(\mu_y,\vect{y},\omega_y)=1 \notag\\
  &\quad\;\land\; \msgV(\mu_z,\vect{z},\omega_z)=1,
    \tag{MSG}\label{eq:msg-check}\\
  &\forall \chi\in\mathcal{S},\,j\in I{:}\quad
    \wireV(\para,\Gamma_{\chi,j},a_{\chi,j},\rho_{\chi,j})=1,
    \tag{WIRE}\label{eq:wire-check}\\
  &\forall v\in\mathcal{W},\,j\in I{:}\quad
    a_{v,j}=\enc(v)_j,
    \tag{RS}\label{eq:rs-check}\\
  &\forall j \in I{:}\quad
    a_{x,j} = \fold\!\bigl(a_{A,j},\,\vect{r}\bigr), \tag{FOLD-A}\label{eq:fold-A}\\
  &\forall j \in I{:}\quad
    a_{y,j} = \fold\!\bigl(a_{B,j},\,\vect{x}\bigr), \tag{FOLD-B}\label{eq:fold-B}\\
  &\forall j \in I{:}\quad
    a_{z,j} = \fold\!\bigl(a_{C,j},\,\vect{r}\bigr), \tag{FOLD-C}\label{eq:fold-C}\\
  &\forall j \in I{:}\quad
    a_{y,j} = a_{z,j}, \tag{EQ}\label{eq:eq-check}\\
  &\forall \chi \in \mathcal{S},\, j \in I{:}\quad
    \openV(\pi_{\chi,j},L_{\chi,j},\cm_{\chi},j)=1
    \tag{PATH}\label{eq:path-check}
    \\
  &\cpLinkV(\para,T_I,
    \{(\Gamma_{\chi,j},L_{\chi,j})\}_{\chi\in\mathcal{S},\,j\in I},
    \tau_I)=1
    \tag{LINK}\label{eq:link-check}
\end{align}
\endgroup
Here $\forall j \in I$ ranges over every sampled position in the ordered tuple,
including repetitions.
The batch transcript tag in~\eqref{eq:link-check} is
\[
\begin{aligned}
P_I&=\{(\chi,j,\Gamma_{\chi,j},L_{\chi,j})\}_{\chi,j},\\
T_I&=\Hash(\textsf{FMM-link-batch},\mathsf{Cm}_{ABC},\mathsf{Cm}_{XYZ},I,P_I).
\end{aligned}
\]
Equation~\eqref{eq:wire-check} is the critical bridge between the private
Groth16 witness and the auxiliary opening world: the fold equations use
$a_{\chi,j}$, and the circuit simultaneously proves that this same value opens
the public handle $\Gamma_{\chi,j}$.
Equation~\eqref{eq:path-check} uses the selected position-opening verifier on
the compact leaf handle $L_{\chi,j}$.
For the transparent Merkle instantiation, this is $\merkleV$ with the queried
index included in the leaf domain.
Equation~\eqref{eq:link-check} then proves that the SNARK-side handle
$\Gamma_{\chi,j}$ and the external Merkle leaf handle $L_{\chi,j}$ bind the
same sampled object value.
Equation~\eqref{eq:msg-check} binds the message vectors before $I$ is sampled.
Equation~\eqref{eq:rs-check} computes the sampled RS/code evaluation for each
intermediate vector inside the circuit.
In the $\fmQA$ artifact, the message opening, wire-handle openings, sampled RS
evaluations, and fold equations are included in the Groth16 relation, while
Merkle path verification and QA-NIZK/CP-link verification are auxiliary checks
bound to the same transcript.
The security proof uses only message-commitment binding, sampled witness-to-leaf
link consistency, and position binding of the opening layer.

The critical property is that the Groth16 relation involves only
$\mathcal{O}(|I| \cdot k)$ constraints for the fold operations, sampled RS
evaluations, wire-handle openings, and message-opening checks.
Merkle authentication and CP-link verification are auxiliary online checks whose
cost is reported separately.
Since $|I|$ is a security-parameter-sized constant independent of $k$, the
in-circuit checking relation is \emph{linear in $k$}.

\paragraph{Intermediate-binding cost}
The message checks in~\eqref{eq:msg-check} force the prover to commit to fixed
vectors $\vect{x},\vect{y},\vect{z}$ before the query tuple is sampled.
The wire and link checks in~\eqref{eq:wire-check} and~\eqref{eq:link-check}
then force each sampled external opening to equal the value used by the
in-circuit fold relation; for intermediate vectors,
\eqref{eq:rs-check} also forces this value to be the corresponding code
evaluation $\enc(v)_j$.
Without the pre-query message commitment, a cheating prover could choose
sampled openings first and then interpolate a vector that matches only those
positions, defeating the distance-based soundness argument.
Analogously, the input matrix commitments $\cm_A,\cm_B,\cm_C$ must be
well-formed commitments to row-wise encodings of $\mat{A},\mat{B},\mat{C}$.
In our model this is part of the public input-commitment interface, not a
property re-proved by the multiplication protocol itself.
For Reed--Solomon-style encodings, a sampled coordinate $\enc(v)_j$ can be
computed by evaluating the degree-$(k-1)$ message polynomial at the queried
domain point, costing $\mathcal{O}(k)$ constraints per sampled coordinate.
Thus the sampled intermediate checks contribute $\mathcal{O}(tk)$ constraints.
A fallback backend that proves full dense codeword validity inside the circuit
would instead require $\mathcal{O}(k(n-k))$ work for a dense generator matrix.
We discuss the trade-off in Section~\ref{sec:complexity}.

\subsection{Protocol Description}
\label{sec:protocol-desc}

We now give the full specification of $\protocol$.
Let $\mathcal{C}: \mathbb{F}^k \to \mathbb{F}^n$ be a systematic linear code with relative distance $\delta$ and $\merkle$ denote the Merkle tree commitment.
Let $\mathcal{M} = \{\mat{A}, \mat{B}, \mat{C}\}$ be the matrix set, $\mathcal{W} = \{\vect{x}, \vect{y}, \vect{z}\}$ the vector set, and $\mathcal{S} = \mathcal{M} \cup \mathcal{W}$.
The verifier is given certified input commitments
$(\cm_A,\cm_B,\cm_C)$ to $\enc(\mat{A}),\enc(\mat{B}),\enc(\mat{C})$.
The protocol $\protocol$ operates between a prover $\mathcal{P}$ and verifier $\mathcal{V}$ as shown in Figure~\ref{fig:protocol}.

    \mathcal{P} \< \< \mathcal{V} \\[4pt]

    \textbf{Phase 1: Public input} \< \< \\
    \text{Certified roots } \cm_A,\cm_B,\cm_C
      \text{ bind to } \enc(\mat{A}),\enc(\mat{B}),\enc(\mat{C}) \< \< \\[4pt]
    \mathsf{Cm}_{ABC}\gets\Hash(\para,\cm_A,\cm_B,\cm_C) \< \< \\[4pt]
    %% Phase 2
    \< \< \textbf{Phase 2: Challenge} \\
    \< \sendmessageleft*[2.5cm]{r} \<
      r \gets \Hash(\textsf{FMM-r},\mathsf{Cm}_{ABC}) \\[4pt]
    %% Phase 3
    \textbf{Phase 3: Respond} \< \< \\
    \vect{r} \gets (1, r, r^2, \dots, r^{k-1}) \< \< \\
    \vect{x} \gets \vect{r}\mat{A},\quad \vect{y} \gets \vect{x}\mat{B},\quad \vect{z} \gets \vect{r}\mat{C} \< \< \\
    \text{For } v \in \mathcal{W}: \< \< \\
    \quad \omega_v \sample \{0,1\}^{\lambda},\quad \mu_v \gets \pedersen(v;\omega_v) \< \< \\
    \quad \enc_v \gets \enc(v),\quad \cm_v \gets \merkle(\enc_v) \< \< \\
    \mathsf{Cm}_{XYZ} \gets \Hash(\para,r,\mu_x,\mu_y,\mu_z,\cm_x,\cm_y,\cm_z)
      \< \sendmessageright*[2.5cm]{\mu_x,\mu_y,\mu_z,\cm_x,\cm_y,\cm_z} \< \\[4pt]
    %% Phase 4
    \< \< \textbf{Phase 4: Query} \\
    \< \sendmessageleft*[2.5cm]{I} \<
      I\gets\textsf{Sample}_t(\Hash(\textsf{FMM-I},\mathsf{Cm}_{XYZ})) \\[4pt]
    %% Phase 5
    \textbf{Phase 5: Open \& Prove} \< \< \\
    \text{For } j \in I,\ \chi \in \mathcal{S}: \< \< \\
    \quad (a_{\chi,j}, \eta_{\chi,j}, L_{\chi,j}, \pi_{\chi,j}) \gets \merkleO(\cm_\chi, j) \< \< \\

      \Gamma_{\chi,j}\gets\wireCom(\para,a_{\chi,j};\rho_{\chi,j}) \< \< \\
    \quad \Delta_{\chi,j}\gets\rho_{\chi,j}-\eta_{\chi,j} \< \< \\

    \tau_I\gets\cpLinkP(\para,T_I,\{(\Gamma_{\chi,j},L_{\chi,j})\},\{\Delta_{\chi,j}\}) \< \< \\

      \mu_x,\mu_y,\mu_z,\, r,\, I,\,
      \{\Gamma_{\chi,j}\}_{j \in I,\chi\in\mathcal{S}} \Big) \< \< \\
    \wit \gets \Big( \vect{x}, \vect{y}, \vect{z},\, \omega_x,\omega_y,\omega_z,\,

      \< \sendmessageright*[2.5cm]{\pi,\{\Gamma_{\chi,j}\},\mathsf{aux}_I} \< \\[4pt]
    %% Phase 6
    \< \< \textbf{Phase 6: Verify} \\
    \< \< b_{\mathsf{snark}} \gets \snarkV(\para, \stmt, \pi) \\

}

\paragraph{Remark on the SNARK relation}
The SNARK proof $\pi$ attests to the in-circuit part of
$\mathcal{R}_{\mathsf{SNARK}}$ defined in Section~\ref{sec:relation-chain};
full transcript acceptance additionally requires the auxiliary opening and
CP-link verifiers to accept.
The implemented verifier checks three groups of conditions, split between the
Groth16 circuit and auxiliary verifiers.
First, constraint~\eqref{eq:msg-check} ensures that the message commitments
$\mu_x,\mu_y,\mu_z$ open to the same $\vect{x},\vect{y},\vect{z}$ used in the
fold checks.
Constraint~\eqref{eq:wire-check} makes each sampled value used by the circuit
open the public wire handle $\Gamma_{\chi,j}$, and
constraints~\eqref{eq:rs-check}--\eqref{eq:eq-check} verify the sampled RS,
fold, and equality checks at each $j \in I$ inside the Groth16 circuit.
Second, the auxiliary CP-link verifier checks~\eqref{eq:link-check}, linking
each public wire handle $\Gamma_{\chi,j}$ to the authenticated external leaf
handle $L_{\chi,j}$.
Third, the auxiliary opening verifier checks~\eqref{eq:path-check} for all
Merkle opening proofs over the leaf handles.
The public statement $\stmt$ consists of the commitment roots
$\{\cm_\chi\}_{\chi \in \mathcal{S}}$, the intermediate message commitments
$\mu_x,\mu_y,\mu_z$, the challenge $r$, the query tuple $I$, and the sampled
wire handles $\{\Gamma_{\chi,j}\}$.
The witness $\wit$ consists of the intermediate vectors, openings of their
message commitments, the sampled matrix columns or vector leaves used by the
fold equations, and the wire-handle opening randomness.

\paragraph{Non-interactive variant}
The protocol as described is a three-round public-coin interactive protocol.
By applying the Fiat--Shamir heuristic~\cite{fiat1987prove} in the random oracle model, it can be made non-interactive using domain-separated transcript hashes:
\[
\begin{gathered}
  \mathsf{Cm}_{ABC}\gets\Hash(\para,\cm_A,\cm_B,\cm_C),\\
  r \gets \Hash(\textsf{FMM-r},\mathsf{Cm}_{ABC}).
\end{gathered}
\]
and
\[
\begin{gathered}
  \mathsf{Cm}_{XYZ}\gets
    \Hash(\para,r,\mu_x,\mu_y,\mu_z,\cm_x,\cm_y,\cm_z),\\
  T_{\mathsf{qry}} \gets (\mathsf{Cm}_{ABC},\mathsf{Cm}_{XYZ}),\\
  I \gets \textsf{Sample}_{t}\!\left(\Hash(\textsf{FMM-I},T_{\mathsf{qry}})\right).
\end{gathered}
\]
The resulting non-interactive proof consists of the commitment roots, the
intermediate message commitments, the transcript-derived challenges, the
sampled wire handles $\{\Gamma_{\chi,j}\}$, and the SNARK proof $\pi$.
Merkle leaf handles, authentication paths, and CP-link material are auxiliary
proof data verified by the corresponding backend.
Raw sampled matrix columns are not serialized as proof data; they remain
private Groth16 witness values bound to the public wire handles.

\paragraph{Security of the non-interactive variant}
A potential concern with the Fiat--Shamir transform for proximity-based protocols is a \emph{grinding attack}: a malicious prover could try many transcript prefixes until the derived challenge $r$ or query tuple $I$ is favorable.
The random-oracle theorem accounts for this by the standard
$\epsilon_{\mathsf{FS}}(q_H)$ loss in Theorem~\ref{thm:security}.
For intuition, consider grinding only the intermediate commitments after $r$ is fixed.
Suppose the adversary has committed to $(\cm_A, \cm_B, \cm_C)$ (and hence to fixed encoded matrices) and, after receiving $r$, is searching for intermediate message commitments and encoded-vector roots such that the transcript-derived query tuple $I$ avoids the disagreement set $D$ of some fold or equality check.
If any of the four checks fails globally, then $|D| \ge \delta n$ by the minimum-distance property.
For a single random query $j \in [n]$, the probability of $j \notin D$ is at most $1 - \delta$; for $t$ independent queries it is $(1-\delta)^t$.
Choosing $t$ as in Section~\ref{sec:security} makes the union-bounded proximity term $4(1-\delta)^t$ at most $2^{-\lambda}$.
Each trial of the grinding attack produces an independently random $I$ in the random oracle model because the query hash binds the full transcript, so the probability that $q$ grinding attempts yield a favorable $I$ is at most $q \cdot 4(1-\delta)^t$.
For any $\ppt$ adversary, $q$ is polynomially bounded in $\lambda$, giving a total success probability of $\mathsf{negl}(\lambda)$.
Hence the non-interactive protocol retains the soundness bound of
Theorem~\ref{thm:security} in the random oracle model, plus the stated
Fiat--Shamir loss.

\paragraph{Zero-knowledge extension}
The protocol as stated is a \emph{verifiable computation} protocol and does not conceal the inputs $\mat{A}, \mat{B}, \mat{C}$ from the verifier.
We do not claim zero knowledge for $\protocol$.
A zero-knowledge variant would require replacing the Merkle tree commitments
with hiding commitments, using a zero-knowledge SNARK backend for $\pi$, and
masking the intermediate vectors and sampled openings so that the transcript
does not reveal linear information about the committed matrices.
The backend code-commitment and linking material would also need a separate
simulation argument.
We therefore treat zero knowledge as future work rather than as a property of
the construction analyzed in this paper.


\subsection{Complexity Analysis}
\label{sec:complexity}

We analyze the costs of $\protocol$.

\paragraph{Prover computation}
The prover's dominant costs are:
\begin{enumerate}[label=(\roman*)]
  \item \emph{Matrix multiplication}: Computing $\mat{C} = \mat{A}\mat{B}$ requires $\mathcal{O}(k^3)$ field operations (or $\mathcal{O}(k^\omega)$ with fast algorithms). This is performed natively outside the SNARK circuit and is amenable to GPU acceleration.
  \item \emph{Encoding}: $3k$ rows (one per matrix row, three matrices) each encoded into length-$n$ codewords costs $\mathcal{O}(kn)$ per matrix with linear-time codes.
  \item \emph{Vector computation}: Computing $\vect{x}, \vect{y}, \vect{z}$ costs $\mathcal{O}(k^2)$ in total.
  \item \emph{SNARK proving}: The circuit size is $\mathcal{O}(t \cdot k + E_{\mathsf{msg}}(k))$ for the fold checks, sampled RS evaluations, wire-handle openings, and message-opening constraints. Merkle and CP-link work is auxiliary and is included in the reported proving, verification, and proof-size breakdowns.
\end{enumerate}

\paragraph{Verifier computation}
The verifier performs SNARK verification together with any commitment/linking
checks required by the chosen backend.
For a pairing-based SNARK whose public input consists only of the roots,
challenge, and query indices, the core SNARK verification is $\mathcal{O}(1)$.
For transparent or linking-heavy backends, verification may scale with the
public input or linking proof size; the concrete behavior is reported in
Section~\ref{sec:implementation}.

\paragraph{Communication}
The communication depends on the commitment layer.
With the QA-NIZK/Merkle implementation evaluated in this paper, the proof
contains the SNARK proof, message commitments, public wire handles,
authentication paths, and CP-link material for the queried objects.
The raw sampled matrix columns contain $\mathcal{O}(tk)$ field elements, but
they are Groth16 witness values rather than serialized proof bytes.
The serialized auxiliary material is compact: wire/leaf handles, Merkle paths,
and link proofs scale as $\mathcal{O}(t\log n+E_{\mathsf{link}}(k))$ for fixed
security parameter.
This accounting explains the sub-megabyte online proof sizes reported in
Section~\ref{sec:implementation} and Appendix~\ref{app:eval-details}; making
the sampled columns public would instead add $\Theta(tk)$ field elements.

\paragraph{Circuit size comparison}
Table~\ref{tab:cost-summary} summarizes the asymptotic costs.
Na\"ive arithmetization uses $\mathcal{O}(k^3)$ constraints.
Freivalds' algorithm alone uses $\mathcal{O}(k^2)$.
The online checker achieves
\[
  \mathcal{O}\bigl(tk + E_{\mathsf{msg}}(k)\bigr)
  \text{ in-circuit work}
\]
plus $\mathcal{O}(t\log n+E_{\mathsf{link}}(k))$ auxiliary opening/linking
work.
The in-circuit term covers the fold checks, sampled RS evaluations, and
message-opening checks.
The auxiliary term covers Merkle authentication and QA-NIZK/CP-link
verification over compact sampled handles.
The older notation $E_{\mathsf{cc}}(k)$ denotes the combined
message-binding/linking cost, with
$E_{\mathsf{cc}}(k)=E_{\mathsf{msg}}(k)+E_{\mathsf{link}}(k)$ for the current
artifact.
For dense general codes, a full in-circuit codeword-validity fallback gives
$E_{\mathsf{cc}}(k)=\mathcal{O}(k(n-k))$, which is $\mathcal{O}(k^2)$ at
constant rate.
For the CP-linked sampled backend evaluated in this paper, the online sampled
encoding work is already included in the $\mathcal{O}(tk)$ term.
Setting
\[
  t = \left\lceil
    \frac{\lambda+2}{\log_2(1/(1-\delta))}
  \right\rceil
\]
then gives $\mathcal{O}(k)$ in-circuit work and $\mathcal{O}(\log k)$
serialized auxiliary opening material for fixed security parameter, with
concrete sizes discussed in Section~\ref{sec:implementation}.
