\section{Technical Overview}
\label{sec:tech-overview}

We provide a high-level description of our protocol for verifiable matrix multiplication before presenting the formal construction in Section~\ref{sec:construction}.
The central challenge is to verify that a claimed product $\mat{C} = \mat{A}\mat{B}$ for matrices $\mat{A}, \mat{B}, \mat{C} \in \mathbb{F}^{k \times k}$ is correct, while keeping the verifier's work substantially below the $\mathcal{O}(k^3)$ cost of recomputing the multiplication.
Our approach combines three classical ideas---\emph{randomized verification}, \emph{error-correcting codes}, and \emph{succinct commitment schemes}---in a way that decomposes the verification into components that are each efficient to check inside a SNARK circuit.

\subsection{Starting Point: Freivalds' Algorithm and Its Limitations}
\label{sec:overview-freivalds}

The classical starting point for verifying matrix multiplication is Freivalds' algorithm~\cite{freivalds1977probabilistic}.
Given matrices $\mat{A}, \mat{B}, \mat{C} \in \mathbb{F}^{k \times k}$ and a uniformly random vector $\vect{r} \in \mathbb{F}^k$, one checks whether $\vect{r}\mat{A}\mat{B} = \vect{r}\mat{C}$.
If $\mat{A}\mat{B} \neq \mat{C}$, then $\mat{D} \coloneqq \mat{A}\mat{B} - \mat{C} \neq \mat{0}$, and the check $\vect{r}\mat{D} = \vect{0}$ fails with probability at least $1 - k/|\mathbb{F}|$ by the Schwartz--Zippel lemma.
This reduces a matrix-matrix verification to a vector-matrix computation, collapsing the problem from $\mathcal{O}(k^3)$ to $\mathcal{O}(k^2)$.

However, even the reduced $\mathcal{O}(k^2)$ cost is prohibitive when the check must be performed \emph{inside a SNARK circuit}.
In an R1CS or Plonk arithmetization, each field multiplication corresponds to a constraint, so encoding the vector-matrix products $\vect{r}\mat{A}$, $\vect{r}\mat{B}$, and $\vect{r}\mat{C}$ directly would still produce $\mathcal{O}(k^2)$ constraints.
For matrices arising in modern deep-learning inference (where $k$ can reach thousands), this SNARK circuit cost remains impractical.

\subsection{From Vectors to Codewords: Leveraging Linear Codes}
\label{sec:overview-encoding}

Our key observation is that the \emph{linearity} of error-correcting codes can be used to move most of the computation outside the circuit while preserving verifiability.
Concretely, suppose that each row of a matrix $\mat{M} \in \mathbb{F}^{k \times k}$ is encoded using a systematic linear code $\mathcal{C}: \mathbb{F}^k \to \mathbb{F}^n$ with relative distance $\delta$.
We write $\widehat{\mat{M}} := \enc(\mat{M})$ for the row-wise encoding of $\mat{M}$, whose $i$-th row is $\mathcal{C}(\mat{M}[i,*])$.
Because $\mathcal{C}$ is $\mathbb{F}$-linear, a linear combination of codewords is the codeword of the corresponding linear combination of messages:
\begin{equation}\label{eq:linearity}
  \sum_{i=1}^{k} r_i \cdot \widehat{\mat{M}}[i,*]
  =
  \enc\!\left(\sum_{i=1}^{k} r_i \cdot \mat{M}[i,*]\right).
\end{equation}
Equivalently, applying the fold operation column-by-column gives
\begin{equation}\label{eq:fold-encoded-vector}
    \big(
        \fold(\vect{r}, \widehat{\mat{M}}[*,1]),
        \ldots,
        \fold(\vect{r}, \widehat{\mat{M}}[*,n])
    \big)
    =
    \enc(\vect{r}\mat{M}).
\end{equation}
This identity is the engine that allows us to \emph{check vector-matrix products column-by-column in the encoded domain} without materializing the full vectors.

\subsubsection{Commitment via Pedersen commitments and Merkle trees}
\label{sec:overview-commitment}

Each encoded matrix $\widehat{\mat{M}}$ is first committed column-by-column using
Pedersen vector commitments. Let $\ck$ be a fixed Pedersen commitment key for
vectors in $\mathbb{F}^k$. For each column $j\in[n]$, the prover samples
$o_{M,j}\sample\mathbb{F}$ and computes
\[
  \cm_{M,j}
  \gets
  \pedC(\ck,\widehat{\mat{M}}[*,j];o_{M,j}).
\]
This produces a vector of Pedersen commitments
\[
  \vect{\cm}_M
  =
  (\cm_{M,1},\ldots,\cm_{M,n}).
\]
The prover then commits to this vector using a Merkle tree:
\[
  \rt_M
  \gets
  \merkleC(\vect{\cm}_M).
\]
Equivalently, the leaves of the Merkle tree are the Pedersen commitments to the
encoded columns of $\widehat{\mat{M}}$. All column commitments use the same
Pedersen commitment key $\ck$.

For each $\mat{M}\in\{\mat{A},\mat{B},\mat{C}\}$, the prover first commits to
each encoded column $\widehat{\mat{M}}[*,j]$ using a Pedersen commitment:
\[
    \cm_{M,j}
    \gets
    \pedC(\ck,\widehat{\mat{M}}[*,j];o_{M,j})
    \quad \text{for each } j\in[n].
\]
It then collects these commitments into a vector and commits to this vector
using a Merkle tree:
\[
    \vect{\cm}_M
    \coloneqq
    (\cm_{M,1},\ldots,\cm_{M,n}),
    \quad
    \rt_M
    \gets
    \merkleC(\vect{\cm}_M).
\]
The prover sends the roots $(\rt_A,\rt_B,\rt_C)$ before the Freivalds challenge
$\vect{r}$ is sampled. These roots bind the prover to the Pedersen commitments
of all encoded columns, while each Pedersen commitment binds the corresponding
encoded column $\widehat{\mat{M}}[*,j]$.


\subsection{Proximity-Based Verification via Random Sampling}
\label{sec:overview-proximity}

After the Freivalds reduction, the verification task becomes: given committed
encoded matrices $\widehat{\mat{A}}, \widehat{\mat{B}}, \widehat{\mat{C}}$ and
a random challenge vector $\vect{r}$, check that the intermediate vectors
\[
  \vect{x} = \vect{r}\mat{A}, \quad
  \vect{y} = \vect{x}\mat{B}, \quad
  \vect{z} = \vect{r}\mat{C}
\]
satisfy $\vect{y}=\vect{z}$.
We now explain how to verify these relations in \emph{linear} time using the
encoding.

The prover computes $\vect{x},\vect{y},\vect{z}$ outside the SNARK and encodes
them as
\[
    \widehat{\vect{x}} \coloneqq \enc(\vect{x}), \quad
    \widehat{\vect{y}} \coloneqq \enc(\vect{y}), \quad
    \widehat{\vect{z}} \coloneqq \enc(\vect{z}).
\]
For each intermediate vector $\mathcal{W}\in\{\vect{x},\vect{y},\vect{z}\}$, the prover sample  $o_{\mathcal{W}}\sample\mathbb{F}$ and computes a Pedersen commitment $\cm_{\mathcal{W}} \gets \pedC(\ck,\mathcal{W};o_{\mathcal{W}})$.
The prover also commits to the encoded coordinates of $\widehat{\vect{x}},\widehat{\vect{y}},\widehat{\vect{z}}$, and sends these commitments before the query tuple is sampled.
The pre-query vector commitments $(\cm_{\vect{x}},\cm_{\vect{y}},\cm_{\vect{z}})$ are needed because the sampled Merkle openings alone only fix the queried coordinates; without pre-query commitments to $\vect{x},\vect{y},\vect{z}$, the prover could choose vectors after seeing $I$ that fit only those sampled positions.

The verifier then samples an ordered tuple
$I=(j_1,\ldots,j_t)\sample[n]^t$ of column indices independently.
For each sampled $j\in I$, the prover supplies the $j$-th encoded column or
coordinate as SNARK witness data, publishes a witness commitment bound to the
relevant witnesses by the CP-SNARK backend, and provides auxiliary
opening/linking material. The auxiliary material links the full intermediate
vector witnesses to the pre-query vector commitments
$(\cm_{\vect{x}},\cm_{\vect{y}},\cm_{\vect{z}})$ and links the sampled encoded
witnesses to the external Pedersen commitments.

At each queried position $j$, the verifier checks four \emph{local consistency
equations}:
\begin{enumerate}[label=(\roman*)]
  \item
  $\widehat{\vect{x}}[j]
  =
  \fold\!\big(\vect{r},\widehat{\mat{A}}[*,j]\big)$,
  ensuring $\vect{x}=\vect{r}\mat{A}$;

  \item
  $\widehat{\vect{y}}[j]
  =
  \fold\!\big(\vect{x},\widehat{\mat{B}}[*,j]\big)$,
  ensuring $\vect{y}=\vect{x}\mat{B}$;

  \item
  $\widehat{\vect{z}}[j]
  =
  \fold\!\big(\vect{r},\widehat{\mat{C}}[*,j]\big)$,
  ensuring $\vect{z}=\vect{r}\mat{C}$;

  \item
  $\widehat{\vect{y}}[j]
  =
  \widehat{\vect{z}}[j]$,
  ensuring the Freivalds check $\vect{y}=\vect{z}$.
\end{enumerate}

The crucial point is that each of these checks involves only a \emph{single
column} of the encoded matrices---an inner product of length $k$ for the fold
operations plus a scalar comparison.
Hence the total verifier work per query is $\mathcal{O}(k)$, and for $t$
queries the total is $\mathcal{O}(tk)$.




\paragraph{Why does sampling suffice?}

The prover commits to the encoded matrices and to the intermediate vectors
before the query positions are sampled. The vector-level CP-link proofs ensure
that the vectors used inside the SNARK are the same vectors committed before
the queries are chosen.

At each sampled position $j$, the SNARK relation recomputes the corresponding
codeword symbols, such as $\widehat{\vect{x}}[j]$, $\widehat{\vect{y}}[j]$, and
$\widehat{\vect{z}}[j]$, from the committed vector witnesses. It also checks that
these symbols are consistent with the opened Merkle leaves, namely the
Pedersen commitments to the queried encoded columns.

The verifier therefore does not need to encode the full vectors. It only
verifies the SNARK proof together with the sampled Merkle openings and linking
proofs.

Suppose that one of the checked vector relations is false. For example, if
$\vect{y}\neq \vect{z}$, then $\enc(\vect{y})$ and $\enc(\vect{z})$ are distinct
codewords. Since $\mathcal{C}$ has relative distance $\delta$, these two
codewords differ in at least a $\delta$-fraction of positions. Hence a
uniformly sampled query position detects this inconsistency with probability at
least $\delta$. With $t$ independent queries, the probability that this false
relation is not detected is at most $(1-\delta)^t$.

Applying a union bound over the four vector relations
\[
  \vect{x}=\vect{r}\mat{A},\qquad
  \vect{y}=\vect{x}\mat{B},\qquad
  \vect{z}=\vect{r}\mat{C},\qquad
  \vect{y}=\vect{z},
\]
the proximity-checking failure probability is at most $4(1-\delta)^t$.
Thus, by setting
$
  t
  =
  \left\lceil
    \frac{\lambda+2}
         {\log_2(1/(1-\delta))}
  \right\rceil,
$
this term is bounded by $2^{-\lambda}$.

\subsection{Putting It Together: The Full Protocol Pipeline}
\label{sec:overview-pipeline}

Combining the ingredients above, our protocol $\protocol$ proceeds as follows (see Figure~\ref{fig:protocol} for the formal description).

\paragraph{Commit inputs}
The prover row-wise encodes $\mat{A},\mat{B},\mat{C}$ and sends roots
$(\cm_A,\cm_B,\cm_C)$.
The roots are fixed before the Freivalds challenge and bind to those row-wise
encodings under the linear code $\mathcal{C}$.

\paragraph{Challenge}
The verifier samples a random field element $r \in \mathbb{F}$ and sends it to the prover.
This induces the structured challenge vector $\vect{r} = (1, r, r^2, \ldots, r^{k-1})$.

\paragraph{Respond}
The prover computes the intermediate vectors $\vect{x} = \vect{r}\mat{A}$,
$\vect{y} = \vect{x}\mat{B}$, $\vect{z} = \vect{r}\mat{C}$, commits to the
vectors, encodes them, and commits to the encoded leaves
$(\cm_x,\cm_y,\cm_z)$.

\paragraph{Query}
The verifier samples $I=(j_1,\ldots,j_t) \sample [n]^t$ and sends the sampled
indices to the prover.
The prover supplies the corresponding sampled columns or vector leaves as
Groth16 witness data, together with public SNARK-side commitments and auxiliary
Merkle openings for compact leaf handles.

\paragraph{SNARK verification}
The verifier checks sampled RS evaluations for intermediate vectors and the four
local consistency equations at each queried index through the Groth16 proof.
The CC-SNARK interface binds the full vector witnesses and sampled witness
values to public SNARK-side commitments.  Merkle path validity, vector-level
linking to the pre-query vector commitments, and sampled-linking consistency
over the public leaf handles are auxiliary verifier checks bound to the same
transcript.
The prover then sends a succinct proof $\pi$ plus the sampled opening/linking
material, and the verifier accepts only if every component verifies.

\paragraph{Cost summary}
The \emph{SNARK circuit size}---the key metric governing prover cost---is
$\mathcal{O}(t \cdot k)$ for sampled folds and RS evaluations.
Vector-level CP-Link, Merkle authentication, and sampled-linking verification
add $\mathcal{O}(t\log n+E_{\mathsf{vec}}(k)+E_{\mathsf{link}}(k))$ auxiliary
online work.
For the sampled-opening backend evaluated in this paper, the in-circuit checker
is linear in $k$ for fixed $t$ and avoids the $k^2$ or $k^3$ circuit costs.
The prover additionally performs the native matrix multiplication ($\mathcal{O}(k^3)$) and encoding ($\mathcal{O}(kn)$) outside the SNARK.
The verifier's core SNARK work is $\mathcal{O}(1)$ for pairing-based backends, or $\mathcal{O}(|\stmt|)$ for transparent ones; total verification additionally depends on the selected commitment/linking backend.
